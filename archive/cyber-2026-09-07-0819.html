Top Story

“StyleSmuggler”: an unpatched Magento and Adobe Commerce zero-day is backdooring stores now

Dutch e-commerce security firm Sansec published an advisory on 5 September describing an unauthenticated remote code execution flaw in Magento Open Source and Adobe Commerce that it named StyleSmuggler. Sansec says attacks began on 4 September and that it went public early because “stores are being compromised right now.” The firm reports it reproduced the full unauthenticated chain on clean installations of 2.4.7, 2.4.8 and 2.4.9, and its first victim was running 2.4.6-p15 with Adobe’s July and August 2026 updates applied — the latest patch level Adobe offers for that release line.

There is no vendor fix. As of 6 September, per The Hacker News, Adobe had published no advisory, no CVE identifier, no patch and no workaround, and its Adobe Commerce security bulletin index listed nothing after the 11 August update. Adobe’s next scheduled security release is Tuesday 8 September; Sansec says it is not yet known whether that release will cover this bug. Sansec’s interim advice for stores not running its own Shield product is to disable GraphQL until a temporary fix lands — Magento hosting firm Disrex Group notes that headless and progressive-web-app storefronts require GraphQL, while most classic and Hyvä storefronts do not.

How it works, as far as it has been published. Sansec’s outline has two stages: the attacker first plants PHP into a file Magento itself writes — a failure report, for instance — then makes Magento execute it by triggering the platform’s standard Payment Transaction Failed Reminder email. The code runs as the message is rendered, so nobody has to open it and the attack succeeds even if delivery fails. Sansec has not yet published the full exploit chain, and has not reproduced it on Adobe Commerce or Adobe Commerce on Cloud; Adobe has not confirmed which versions are affected, and no source has named the attackers.

Indicators of compromise. Sansec and Disrex describe a background process disguised as [kworker/u:8:0] but owned by a non-root user, a binary at ~/.local/share/.gvfsd/gvfsd-user, and a cron line written straight into the spool file that restarts it every five minutes — one store carried that line 1,728 times and the implant re-added it within a second of removal. Sansec’s published check searches var/report/ for the marker X_TRACE_; Disrex says both of its infections were poisoned through var/log/system.log instead and that the header shape has already drifted, so search both directories and match the shape rather than the string. Disrex’s repository carries its own warning that it was written with AI assistance during a live incident and has not been reviewed; both firms’ readings of where the chain ends are unconfirmed by Adobe, and neither the number of compromised stores nor any attribution has been established.

Also Exploited

Elementor Pro flaw is being exploited against WordPress sites — and most installs are still vulnerable

WordPress security firm Defiant warns that threat actors are exploiting CVE-2026-32475 (CVSS 9.8), an arbitrary file upload issue in the Elementor Pro form-submission handler. When the plugin’s validation loop hits an upload slot marked empty it triggers an error and returns, so every remaining file in that field is written to disk unchecked. An attacker submits an upload field as an array — an empty slot to trigger the return, then a PHP payload — and can then request the uploaded file to execute it. “As a result, an unauthenticated attacker can request the uploaded file to execute their PHP payload on the server,” Defiant explains, noting this could lead to full site compromise. One score conflict surfaced this run and is stated rather than resolved: SecurityWeek and securityonline.info both give 9.8, while one developer write-up gives 9.0. The 9.8 carried here is the figure two of three returns state.

The bug affects all Elementor Pro versions up to 4.2.1 and was patched in 4.2.2 on 19 August. According to Defiant, attackers began exploiting it immediately after the fixes landed, and the firm has blocked over 190,000 exploit attempts to date. Elementor Pro has over 6 million active installations; per WordPress data cited by Defiant, roughly two-thirds of Elementor’s 10 million installations were running a vulnerable version as of 4 September.

Indicators of compromise. Successful exploitation writes a PHP file into /wp-content/uploads/elementor/forms/ — the presence of any PHP file in that directory is a strong IoC. Administrators are also advised to review logs for requests to /wp-admin/admin-ajax.php and to check for backdoors if any evidence of compromise turns up. This flaw carries no CISA KEV entry this run could verify, so no federal deadline is asserted for it.

Patch Priority — unpatched zero-day, and an elapsed deadline

If you run a Magento or Adobe Commerce store, act before you patch anything else — because there is nothing to patch. StyleSmuggler is being exploited now and Adobe has shipped no fix; Sansec’s interim measure is to disable GraphQL, three unofficial mitigations now exist (Disrex, ProxiBlue, Graycore — see below, and note the first two are the same fix and must not be stacked), and Disrex puts two flaw-independent server settings ahead of every rule in its repository: add proc_open to PHP’s disable_functions, and mount /tmp, /var/tmp and /dev/shm noexec so a downloaded binary cannot run. At one compromised store the first four of the six PHP functions the dropper tried were already disabled — proc_open was not, and that is the one it used.

For federal agencies the elapsed deadline still governs. The five KEV entries added on 2 September that were not granted an extension carried a federal remediation deadline of Saturday 5 September 2026 under BOD 26-04. That date has passed. The most severe of the group is CVE-2026-83548 — SonicWall SMA 1000 (CVSS 10.0), an unauthenticated server-side request forgery that SonicWall says it investigated “a case indicating the active exploitation” of; CVE-2026-49869 — Kestra OSS (CVSS 10.0) shares the same score. Agencies past due should treat these as an incident-response matter, not a patch-backlog item.

Second, and newly quantified this morning: if you run MikroTik RouterOS with SSH reachable from the internet, patch and then assume compromise. The Shadowserver Foundation now counts more than 122,500 MikroTik devices with SSH exposed — most of them in Brazil (11,300), the United States (7,100), Indonesia (7,100), the Czech Republic (6,300) and Ukraine (5,100) — and Cybernews notes it is unclear how many remain unpatched. Upgrading alone is not sufficient: MikroTik’s advisory says RouterOS will itself check for compromise and set a device to “Flagged” status, written to the Log as a critical entry, and that even an unflagged device should be inspected for unrecognised scripts, users and configuration. Independent researcher Nick Pratley, who reverse-engineered the silent patch, goes further and recommends “a clean rebuild rather than trusting only automatic cleanup.” The two named log artefacts remain the SSH username -2 and an account called ops; CERT Polska cautions that their absence does not rule out unauthorised activity.

Third in the queue, and the one every desk can action today: update Chrome. CVE-2026-85046 (CVSS 8.8), a V8 type-confusion bug that Google says has a working exploit in the wild, was added to KEV on 4 September with a federal deadline of Friday 18 September 2026. Fixed in Chrome 152.0.7977.82/.83 on Windows and macOS and 152.0.7977.82 on Linux.

Neither StyleSmuggler nor CVE-2026-32475 in Elementor Pro is KEV-listed, and neither carries a federal deadline — the red status here is earned by the elapsed 5 September date, which matches the KEV section below, and by an actively exploited flaw for which no vendor patch exists.

NewExposure

122,500 MikroTik routers are sitting on the open internet with SSH reachable — and the six MikroTrick CVEs now all have scores

Cybernews reported this morning that the Shadowserver Foundation has found more than 122,500 MikroTik devices exposing SSH to the public internet, concentrated in Brazil (11,300), the United States (7,100), Indonesia (7,100), the Czech Republic (6,300) and Ukraine (5,100). How many of those remain unpatched is unknown and the report says so. The same piece closes the scoring gap this page has carried since the story broke: CERT Polska registered six RouterOS CVEs and all six now have published severity ratings — the two that chain into MikroTrick at 9.2 apiece, a kernel-memory disclosure at 8.8, an unauthenticated WebFig file read at 8.7, an SSH rekey-state bypass at 6.9 and TLS server impersonation at 6.3. Independent researcher Nick Pratley, who reverse-engineered MikroTik’s deliberately vague patch, recommends “a clean rebuild rather than trusting only automatic cleanup” for any device that was exposed. MikroTik also sent a push notification through its mobile app about the update — a first for the company, noted by both Cybernews and CERT Polska.

Infostealer

NodeStealer stops stealing and starts watching — keylogger, clipboard and screen capture bolted onto a credential thief

Netskope researchers identified an upgraded Python NodeStealer variant in August 2026 that turns an account-stealing infection into continuous surveillance. The addition that matters is a keylogger built on Python’s pynput library: it writes captured text to a temporary file, ships it to the primary Telegram command-and-control channel every 120 seconds, clears the file and keeps going indefinitely. Clipboard monitoring picks up plain text that is pasted rather than typed, and the malware takes a screenshot when it runs and a second one before its screenshot routine ends, sending both over Telegram — which reaches dashboards, recovery codes and open documents that never touch the keyboard or the clipboard at all.

Two Telegram bots, not one, split the take: one receives an archive of browser credentials, passwords and cookie databases, the other Facebook-specific data. The newest samples query more than 20 Facebook Graph API endpoints, up from two in earlier versions, pulling identity details, contacts, posts, pages, advertising assets, business records and login data — enough for an attacker to run unauthorised ads or burn a company’s ad budget rather than merely hijack one profile. Samples ship as compiled Python bytecode with altered header fields, apparently to obscure the compilation timeline and frustrate automated analysis. Netskope reports the recent activity landing mainly in Asia and North America, financial services the leading sector but the campaign crossing several industries. The published indicator is a filename pattern: keylog({ip}).txt in the temp folder.

Two things this desk is not asserting. Netskope’s report does not identify a confirmed initial delivery method, so no infection route is printed here and defenders should not plan around a single one. And the AI angle is stated exactly as the researchers stated it — repeated, similarly-structured calls carrying decorative emoji labels, a pattern absent from earlier NodeStealer code, which they read as a sign some new code may have been produced with AI assistance. That is an inference about style, not proof of a tool or an author, and it is not evidence for the separate AI-assisted-intrusion story elsewhere on this page.

Network edgeCarried forward

MikroTik’s own advisory, read first-hand — the router will tell you if it was owned

This desk had cited MikroTik’s security bulletin as a source for three editions without ever reading it. It was fetched directly in an earlier edition — not this morning — and it carries a detection mechanism that had not appeared on this page before then. Its two key claims were independently re-corroborated this run from Cybernews, which quotes the same advisory: the “Flagged” status check, and the vendor’s statement that it is “not currently publishing detailed information.” The vendor page, dated 3 September, says RouterOS “will check if your device has been compromised, and set it to ‘Flagged’ status if it is” — written to the Log section as a critical entry, with recovery steps on MikroTik’s Flagged-status documentation page. The vendor adds the warning that matters for anyone reading a clean log: even a device that is not Flagged should be inspected after upgrading for unrecognised scripts, users and configuration. That is the vendor’s own instruction, and it lines up with Costin Raiu’s separate caution below that the absence of a failed-login artefact proves nothing.

Two further things the vendor page settles. First, MikroTik is deliberately withholding technical detail — “To give time to update your systems, we are not currently publishing detailed information” — and says the article will be updated in due time, which is why no vendor CVE or CVSS is quoted anywhere on this page. Second, the vendor’s fixed-build list is exactly four: 7.25 beta 3, 7.24.2, 7.23.4 and 6.49.21. That matches CERT Polska exactly, so two independent sources now list four builds against Security Affairs’ five. It does not settle the divergence recorded below, and this desk will not read it as a refutation: Security Affairs dates 7.23.5 to 4 September, a day after this vendor page was written, so a page that predates a build is not evidence against it. Both lists stay printed with their own names on them.

One note of caution about the vendor’s framing. MikroTik calls this “an important security update” but says “most configurations are not at risk” and that for “regular home device users the issue does not pose an immediate risk.” That is a materially calmer reading than CERT Polska’s, which describes active exploitation since 2 September. Both are printed as each party stated them; this desk does not adjudicate between the vendor’s risk assessment and the CERT’s.

Network edge

MikroTrick gets an independent breakdown — and a clock on the public exploit

Security Affairs reported today that Costin Raiu published a technical breakdown of the MikroTik RouterOS exploitation on 5 September, the same day CERT Polska issued its advisory. His framing is blunt: “If you have a MikroTik router on the internet with SSH open, it may already be compromised.” He also makes the zero-day case explicitly — MikroTik shipped fixes on 3 September but exploitation started on 2 September, which he reads as “someone got hold of the news the patches were dropping and began exploiting it at scale.”

A fifth patched build, not in the CERT Polska list. Security Affairs gives the patched versions as 7.25beta3, 7.24.2, 7.23.4, 7.23.5 (released 4 September) and 6.49.21. That is an addition to, not a contradiction of, the four builds CERT Polska named — its advisory predates the 4 September release. Both lists are printed as their own source gives them; this desk does not merge them into a single claim about what MikroTik shipped.

What to look for, and what not to conclude from its absence. Failed logins carry the username -2, which is not a valid account; a successful attack shows in /system history as ssh:-2@<IP>. Raiu’s rule: when that entry is attached to a configuration action — creating or modifying users, SSH keys, scripts, schedulers, services, firewall rules, proxies, tunnels or packet-sniffing settings — treat it as confirmed compromise unless it came from an authorised test. And “do not assume the device is safe merely because no -2 login failure appears: logs may have rolled over or cleaned.”

Infrastructure. 82.192.72.4 is described as a Leaseweb address hosting a busybox binary — a MIPS build from 2010, identical to the official BusyBox 1.16.1 precompiled binary — alongside ftpsrv.py, launch.sh and serve.py; three of the four had no VirusTotal detections at the time of writing. CERT Polska separately noted something it had not seen before: MikroTik pushed warnings to users through its official mobile app.

The exploit is not public yet, and that is the window. Raiu tested reproducibility with four AI tools. Astra refused on safety grounds and suggested he apply for cyber verification; Sol, Daybreak Blue and GLM-5.3 were willing but none produced a working implementation. He puts the gap at one to two days before a working proof of concept lands on GitHub. Raiu’s own Medium post has never been fetched by this desk — every quotation and figure above is as Security Affairs reports it, and is attributed accordingly.

E-commerceCarried forward

StyleSmuggler — first confirmed victims, and one host that saw it live

Independent of Sansec, Magento hosting and development firm Disrex Group published an incident-response repository on 5 September saying it handled two stores compromised on 5 September and a third that was attacked but not breached. One of them ran Magento 2.4.7-p2, a patch level Adobe’s version history dates to August 2024 and eight levels behind current. The store Disrex labels Store A was a Sansec Shield customer and was hit at 23:10 UTC on 4 September, hours before Sansec’s blocking rules went live. On one store the implant made no outbound connection at all, holding 28 connections to the store’s own Redis instance on port 6379 and reading Magento session storage from it. Disrex recorded 26 distinct source addresses across the two stores and says blocking the single attacker address in Sansec’s advisory would have stopped less than a quarter of the traffic it saw. Hosting providers Nexcess and Liquid Web posted identical precautionary notices on 5 September; neither claims a confirmed customer compromise.

E-commerce

Two developers wrote the same StyleSmuggler fix without talking — and the scanner missed the implant

The Hacker News’ report was fetched directly in an earlier edition, not this morning, and carries a post-publication update, sourced to Disrex co-founder Rick Bouma, that materially changes what a merchant can do today. With no vendor fix, three unofficial mitigations are now in circulation — from Disrex, ProxiBlue and Graycore.

The convergence is the story. Disrex’s main mitigation adds a check to three methods in Magento’s dependency-injection code scanners so they cannot run outside the command line. A GitHub user, ProxiBlue — whom Bouma identifies as Magento developer Lucas van Staden — published the same guard on 5 September without coordination: the same three scanner methods, the same PHP_SAPI !== 'cli' check, the same exception message. Disrex has reproduced ProxiBlue’s patches in its own repository with credit, warns that the two are the same fix and must not be applied on top of each other, and regards the independent convergence as strong corroboration that it is the right one. Graycore, LLC published a separate Magento module hardening three points on the chain. Neither Sansec nor Adobe has confirmed that these scanners are where the chain ends, and Graycore’s own README says “that is hardening, not a fix.” One caution carried from the source: one of the three files, ClassesScanner.php, is called over HTTP by at least one third-party module, so guarding it breaks that module’s admin screen.

The scanner reported a compromised store clean. eComscan ran on Store A at 10:00 UTC on 5 September, roughly eleven hours after the implant first ran and while 1,728 cron lines were present, and returned clean. Disrex attributes this to scope rather than a scanner fault: the scheduled scan pointed at the store’s document root, and the implant had installed one directory above it, under the account’s home directory. The lesson is a scan path, not a product verdict.

The implant, and the tell that found it. Disrex describes the binary as a stripped, statically linked Rust program of roughly 1.9 MB built for x86-64 and arm64, and notes the build running in memory on one store differed from the file on disk — so hash /proc/<pid>/exe as well as the file. What actually surfaced one of the two compromises was an email: the store sent its own owner a failed-transaction notice whose template variables were never resolved — a body of raw {{var …}} tags, a customer address on a .invalid domain and a total of zero. It reads like a broken order, Bouma said, but it is exhaust from the exploitation attempt passing through Magento’s template filter. Disrex calls it the single most useful early-warning sign for merchants because noticing it needs no tooling.

Two corrections travel with the update and are printed rather than smoothed over: Bouma revised the compromised stores’ versions and first-contact times — Store A ran 2.4.8 and was hit at 23:10 UTC on 4 September, Store B ran 2.4.7-p2 and was first hit at 00:55 UTC on 5 September — and an earlier count of 28 attacker source addresses was reduced to 26 after two of Disrex’s own verification servers were removed — a different 28 from the 28 Redis connections described in the card above, which are unrelated. Both stores were contained the same day, and Disrex reports no exfiltration, no rogue admin accounts, no payment skimmer and no database backdoor.

AI securityCarried forward

CrowdStrike launches SafeMind, built with NVIDIA

CrowdStrike used Fal.Con 2026 in Las Vegas to unveil SafeMind, a family of purpose-built security models and harnesses the company calls the first agentic system engineered specifically for cyber defenders — a move away from generic frontier models toward something that runs natively inside the Falcon platform. It pairs an offensive component, Red Tempest, trained to emulate AI-driven adversaries and probe for exploitable attack paths, with a defensive counterpart, Blue Solano, built to close those gaps using measures drawn from real incident response. Both were trained on Falcon sensor telemetry — a dataset CrowdStrike’s Kurtz called the largest in the world, drawn from “the trillions of events Falcon sensors see every day” and “15 years of stopping breaches” — and built with NVIDIA on its Nemotron open model. Standalone access rolls out through CrowdStrike’s Project QuiltWorks programme. A vendor announcement, published here as such; no independent evaluation of the models was sourced.

AI-assisted intrusionCarried forward

Unit 42: an AI-orchestrated breach to root in under 10 hours

Palo Alto Networks’ Unit 42 documented an intrusion in which a human operator drove frontier AI models and attack-specific agentic frameworks to compromise an enterprise, harvest master credentials and hijack the victim’s own cloud AI compute in less than 10 hours — work Unit 42 says would otherwise take several red-team operators roughly two weeks. No zero-day was involved: entry came through a publicly reachable web service, after which sub-agents handled reconnaissance, secret-hunting in source repositories, privilege escalation, lateral movement and collection, covering more than 50 MITRE ATT&CK techniques. Stolen repository secrets opened the secrets-management platform and from there root. Branch protection held — an attempt to plant backdoors in Terraform configuration was blocked by mandatory reviews and protected branches. The operators left behind an 80-page assessment of the victim’s security posture. Unit 42’s guidance: treat AI endpoints, API keys, MCP gateways and agents as core enterprise infrastructure, and inventory them accordingly.

BackdoorsCarried forward

“Toy Ghouls” hides C2 inside HiveMQ and Element

Kaspersky’s Securelist describes two new Windows backdoors — mqtt-bird-agent 0.1.0 and matrix-bird-agent 0.1.0 — from the financially motivated group tracked as Toy Ghouls, first observed in early July 2026. The pair take command and control over the HiveMQ MQTT broker and the Element/Matrix messenger respectively, so beacon traffic resembles ordinary SaaS chatter; a config:set_interval message tunes command and telemetry timing. They are post-compromise tooling, dropped only after the group already holds valid administrative access, typically via Evil-WinRM and WinRM-fs. Observed filenames include cplsupport.exe and wtass.exe; the backdoors run interactively or install as Windows services. Reported targeting is of Russian organisations.

CISA KEV & Federal Deadlines

CISA added seven vulnerabilities to the Known Exploited Vulnerabilities catalog on Wednesday 2 September 2026. Remediation windows are set under BOD 26-04, “Prioritizing Security Updates Based on Risk” — risk-based windows that supersede BOD 22-01’s uniform three weeks.

  • Due Saturday 5 September 2026 (overdue by 2 days) — CVE-2026-83548 (SonicWall SMA 1000 SSRF, 10.0), CVE-2026-83549 (SonicWall SMA 1000 post-auth OS command injection, 7.8), CVE-2026-9586 (Sangoma Switchvox SQL injection, 9.3), CVE-2026-82329 (JFrog Artifactory improper authentication, 9.8) and CVE-2026-49869 (Kestra OSS command injection, 10.0).
  • Due Wednesday 16 September 2026 (9 days left) — CVE-2026-48710 (Kludex Starlette request smuggling, 6.5) and CVE-2026-59822 (Berri LiteLLM improper authentication, 8.8).
  • Added separately on Friday 4 September — due Friday 18 September 2026 (11 days left) — CVE-2026-85046, the Google Chromium V8 type-confusion zero-day (CVSS 8.8), on a 14-day window. Google acknowledged that “an exploit for CVE-2026-85046 exists in the wild”; it is the sixth Chrome zero-day exploited in 2026, was reported by researcher Salvatore Gulizia on 4 August, and is fixed in Chrome 152.0.7977.82/.83 (Windows, macOS) and 152.0.7977.82 (Linux). The 18 September date is attributed to reporting; the countdown above is computed from today, Monday 7 September, to 18 September. CISA’s own alert page has returned empty on every previous run that attempted it; it was not re-attempted this morning, and no fetch of it is claimed here. Both dates were re-checked this run and neither moved. CISA’s alert titles again return exactly two September pages — “CISA Adds Seven…” dated 2 September and “CISA Adds One…” dated 4 September — and the seven and the one match the CVEs listed above, item for item. No 5, 6 or 7 September addition exists — which is what a weekend followed by a federal holiday looks like: eight KEV entries in September to date, unchanged for six consecutive runs. The date has now rolled, so every countdown on this page was recomputed from today rather than carried forward: 18 September is 11 days out, 16 September 9 days, and the 5 September group is two days overdue. One independent corroboration this run: a return covering the week of 31 August to 6 September counts 10 KEV additions across that span — the two added on 31 August plus this month’s seven and one, consistent with the eight above rather than a competing figure.
  • One reported discrepancy, stated rather than resolved. The Hacker News, citing the CISA alert, places every CVE except 48710 and 59822 in the 5 September group — which puts Kestra there. SecurityWeek instead describes a three-day window “except for the Kestra and Starlette flaws, which should be patched within two weeks.” Two of three returns this run put Kestra on 5 September and that is what is printed above; the conflict is noted rather than hidden. CISA’s alert page has returned empty on every fetch this desk has attempted, and it was not re-attempted this run, so these dates are attributed to reporting.
  • No KEV entry and no deadline asserted for StyleSmuggler (which has no CVE at all), Elementor Pro (CVE-2026-32475), the MikroTik RouterOS chain, or ASUS Control Center Enterprise — all three are exploited or maximum-severity, but none could be confirmed KEV-listed this run.
